## 1. 概要

独自の実行エンジンを実装するのではなく、SQLを句の境界ごとに分解した「そのステップまでのSQL」を組み立てて、**本物のPostgreSQLに実際に投げて**結果を取得する方式。入力したSELECT文を、論理的な実行順序ごとに分解し、各ステップまでの中間結果テーブルを表示する(INSERT/UPDATE/DELETE文の分解は[5節 Phase B](#phase-b-dml文insertupdatedeleteへの対応-2026-11-03実装済み)を参照)。

実行順序: `FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT[DISTINCT] → ORDER BY → LIMIT/OFFSET`。元クエリに存在しない句のステップは表示しない。

## 2. 機能詳細

### (a) ステップ分解・データ変化の可視化

- 実装: `backend/app/sql_steps.py` の `_build_step_nodes` / `parse_to_steps` / `execute_steps`
- 各ステップの実行結果は `SELECT * FROM (<ステップSQL>) LIMIT 200` でプレビュー行数を保険的に制限([実行時の安全策](../backend/core.md#実行時の安全策)と共通の考え方)

### (b) ステップ0「実行前(元テーブル)」

FROM句が参照する実テーブルを再帰的に特定し(自己結合・多段JOINにも対応)、JOIN・絞り込みが行われる前の生データを表示する。**「実行」ボタンを押す前から**、SQL入力に対して自動(デバウンス500ms)で表示される。INSERT/UPDATE/DELETE文では、対象テーブルを先頭に、FROM/USING句・INSERTのSELECT文が参照するテーブルを続けて表示する(5節Phase B)。

- 実装: `backend/app/sql_steps.py` の `_extract_from_sources` / `_dml_sources` / `preview_source_tables`

### (c) カラムハイライト

各ステップが「どの列を根拠に判断したか」を、pglastのASTから抽出して自動ハイライトする。

| ステップ | ハイライト対象 |
|---|---|
| FROM/JOIN | JOIN条件(ON句)で参照されている列 |
| WHERE | WHERE条件式で参照されている列 |
| GROUP BY | グルーピング対象列 |
| HAVING | HAVING条件式で参照されている列(`COUNT(*)`のように列を直接参照しない場合は対象なし) |
| ORDER BY | 並び替え対象列(SELECTのエイリアス指定も可) |
| SELECT / LIMIT・OFFSET | ハイライトなし |

- 実装: `backend/app/sql_steps.py` の `_referenced_column_names`(`pglast.visitors.Visitor` でColumnRefを収集)
- ステップ0の元テーブルにも、直後のJOINで使われる列を先回りしてハイライト

### (d) 表示UI 【旧実装 — 3節の新レイアウトに置き換え済み】

旧実装(縦につながるステップ表示): ページング(1ステップずつの表示切り替え)ではなく、SQL入力欄と0〜Nのステップボタンを画面上部に固定([固定ヘッダーとスクロール連動](../frontend/core.md#固定ヘッダーとスクロール連動)参照)し、その下に全ステップのカードを接続矢印つきで縦一列に常時表示していた(説明文・SQL・結果テーブルを同じカード内に表示)。

- ボタンクリック → 該当ステップの位置までスムーズスクロール
- スクロール位置 → 対応するボタンが自動でハイライト(scrollspy)

## 3. 表示レイアウトの変更仕様

**変更前(旧2-(d))**: ステップごとのカードを画面幅いっぱいで縦に積み上げ、説明文・SQL・結果テーブルを同じカード内に表示していた。

**変更後の仕様(2026-08-31、複数回の見直しを経て確定)**: ステップごとに1枚の**大きなカード**を用意し、そのカードの中を左右2分割する(左: 説明・SQLスニペット、右: 結果テーブル)。ページ・カード自体はスクロールさせず、カード1枚がまるごと次のカードに**入れ替わる**ことでステップを切り替える。

- カード表示エリア(`.step-stage`)は、画面上部の固定ヘッダーを除いた**ビューポートの残り全体にちょうど収まる固定高さ**とし、ページ本体(`window`/`body`)は一切スクロールしない。
- カードの中は左右2カラム構成:
  - **左側**: ステップ番号・ラベル・説明文・SQLスニペット。SQLスニペットは、プレーンテキスト(`<pre>`)ではなく [SQLエディタ](../frontend/core.md#sqlエディタ)と同じ編集可能コンポーネントを**読み取り専用(`readOnly`/`editable={false}`)**で配置する。将来「ステップ単位でSQLを編集し、そのステップ以降を再計算・再可視化する」機能を追加する際に、表示コンポーネントの差し替えが不要になるようにするため。今回のスコープは disabled 表示までで、編集の有効化・再計算ロジックは別途スコープを切る。
  - **右側**: そのステップの結果テーブルのプレビュー。列ハイライト(2-(c))はそのまま適用する。
- ステップの切り替え操作は2通り:
  - **マウスホイール/トラックパッド操作**: カード表示エリア上でのホイール入力を「ページのスクロール」ではなく「1ステップ進める/戻す」という離散的な操作として扱う(`wheel`イベントを`preventDefault`し、累積量が閾値を超えたら`activeIndex`を1つ進め/戻す。連続入力で複数ステップ飛ばないよう短いクールダウンを設ける)。
  - **上下ボタン**: カード右下に▲(前のステップ)/▼(次のステップ)ボタンを常設し、クリックでも1ステップずつ進める/戻せる。
  - 画面最上部の固定ヘッダーのステップ番号ボタン(0〜N)から直接指定ジャンプすることも引き続き可能。
- ステップが切り替わる際は、カード全体がフェード+わずかな上下スライドで入れ替わる(進む/戻るの向きに応じて双方向)。カード内部の結果テーブルは、それとは別に3.1節のFLIPベースのアニメーション(行/列単位)で変化を見せる。
- レスポンシブ: 画面幅が狭い場合(モバイル等)は左右2分割のカードを維持できないため、現行の縦積みレイアウト(2-(d)相当)にフォールバックすることを検討する。具体的なブレークポイントは実装時に決定する。

**この仕様に至るまでの経緯(2026-08-31、複数回の手戻り)**:
1. 最初に「左カラムを通常スクロール、右カラムを`position: sticky`で追従」という案を実装したが、ヘッダー高さの変化で右カラムの位置がずれる、最後のステップまでスクロールしきれない、という問題が発生した。
2. 次に「左カラムを固定高さの`overflow-y: auto`コンテナにし、内部スクロールだけでステップを切り替える(右カラムも同じ固定高さ)」という案に変更したが、依然としてページ全体やカード内部が「スクロールする」という見た目・挙動が残ってしまい、要件(スクロール操作はあってよいが、画面の上下移動という見た目自体をなくしたい)を満たせていなかった。
3. 最終的に、現在の仕様(ステップごとに1枚の大きなカードが丸ごと入れ替わる方式)に変更した。スクロール/ボタンは「入力」としてのみ使い、DOM要素が物理的にスクロールすることは一切なくした。

### 3.1 ステップ切り替え時のアニメーションイメージ

前のステップの結果テーブルから、次のステップの結果テーブルへ切り替わる際の見た目を、操作の種類ごとに定義する。単純なクロスフェードではなく、**その操作が実際に何をしたか**が視覚的にわかるアニメーションにする。

| ステップ種別 | アニメーションイメージ |
|---|---|
| FROM/JOIN | 複数の元テーブルが、1つのテーブルへ連結(マージ)されていくように見せる |
| WHERE / HAVING(行の絞り込み) | 条件に合わない行がその場でフェードアウトして消え、合致する行だけが残る |
| SELECT(列の絞り込み) | 選択されなかった列がフェードアウトして消え、選択された列だけが残る |

GROUP BY / ORDER BY / LIMIT・OFFSET のアニメーションイメージは未定義(下記オープン課題参照)。

**双方向性(重要な要件)**: ステップを進める方向だけでなく、**スクロールを上に戻して前のステップに戻る場合も、上記アニメーションが逆再生されるようにする**(例: JOINで連結されたテーブルは、前段に戻ると再び分離して見える。消えた行・列は前段に戻ると再度現れる)。スクロール方向(上/下どちらに進んでいるか)を検知し、アニメーションの向きをその都度切り替える必要がある。

**実装上の含み**: 単純なフェードイン/フェードアウトの切り替えでは実現できず、行・列に安定した識別子(主キーや列名)を持たせ、同一の行・列がステップをまたいでどう変化したか(残る/消える/合流する)を追跡できる仕組みが必要になる(いわゆるFLIP的な差分トランジション)。手書きCSSでこれを双方向に作り込むのはコストが高いため、[frontend/core.md](../frontend/core.md#オープン課題-カラーとuiライブラリ)で方針決定した **Framer Motion**(`layout`プロパティによる自動FLIPアニメーション、`AnimatePresence`による出入りアニメーション)の採用を前提に設計する。

**オープン課題**:
- [ ] SELECTで選択されなかった列のうち、主キー/ID列は行の同一性を示すために残す(グレーアウト等)か、完全に消すか
- [ ] GROUP BY(複数行が1行に集約される見せ方)・ORDER BY(行の並び替えアニメーション)・LIMIT/OFFSET(範囲外の行が消える見せ方)、それぞれのアニメーションイメージの具体化

**実装への影響**:
- [x] `frontend/src/App.tsx`: ステップごとの大きなカード(`.step-big-card`、内部で左右2分割)が丸ごと入れ替わる構成に変更。`activeIndex`の切り替えは、ページ・カードのスクロールではなく、ホイール入力(`wheel`イベントを`preventDefault`し、累積量が閾値を超えたら1ステップ進める/戻す)と、カードに常設した▲▼ボタンで行う。

- [x] `frontend/src/components/StepTable.tsx`: Framer Motion(`motion`パッケージ)を導入し、3.1節のステップ種別ごとのアニメーション(JOINの連結・行/列の絞り込み)を、進む/戻るの向きに応じた双方向再生つきで実装する。カード全体のフェード+スライドとは別レイヤーとして、テーブル内部の行・列単位のFLIPアニメーションを担当する。
- [x] `frontend/src/index.css`: 大きなカード1枚+左右2分割のレイアウトスタイルを追加。

**実装メモ**(2026-08-31):
- FROM/JOINと「実行前(元テーブル)」間は、行・列単位でのFLIP対応関係が取れない(複数テーブル→1テーブルで形が変わる)ため、テーブル部分をクロスフェード+収束/発散するスケール・移動アニメーションで表現し、行・列レベルの提供元追跡は行っていない。
- 行の同一性は主キーがないため、直前ステップと共通の列の値を暫定的な識別子として使用している(同値の行が複数ある場合は出現順で区別)。`SELECT *` プレビューでは結合元テーブル同士で同名列(例: `customer_id`)が重複するため、列も同様に出現順で識別している。
- GROUP BY / ORDER BY / LIMIT・OFFSET は専用のアニメーションイメージが未定義(オープン課題参照)なため、上記の行・列差分による汎用トランジションにフォールバックしている。
- レイアウト方式は3節冒頭の「経緯」に記載の通り複数回変更しており、最終的に「大きなカード1枚が丸ごと入れ替わる」方式に落ち着いた。
- 固定ヘッダーの高さ測定に`ResizeObserver`の`contentRect`を使うと、padding/borderを含まない内容ボックスの高さしか取れず、カード表示エリアの高さ計算が実際より小さくなる(ヘッダーの上下パディング+ボーダー分だけカード下端が画面下にはみ出し、`overflow: hidden`で隠れた下端のボタンが見えなくなる)バグがあった。`el.offsetHeight`(border-box)で測り直すことで解消した。

### Phase A: SELECT文の拡充 【2026-09-05実装済み】

既存の「句ごとに分解して本物のPostgreSQLに実行させる」モデルをそのまま拡張できる範囲。優先度は上から順。

- [x] CTE(WITH句) — 非再帰のみ対応(`WITH RECURSIVE`は明示的に未対応エラー)。各CTEの結果を計算する「WITH `<name>`」ステップを、FROM/JOINより前に(複数あれば定義順に)追加する。CTE本体自体はさらに句分解せず、「計算済みの1つの結果」として1ステップで見せる。以降の各ステップのSQLには、CTE名を解決できるよう元のWITH句をそのまま付与して単独実行可能にしている。実装: `backend/app/sql_steps.py` の `_build_step_nodes`(CTE部分)・`_clone_with`
- [x] サブクエリ — スカラサブクエリ・`IN`/`EXISTS`は、既存の句分解モデルにそのまま乗る(WHERE/SELECT等の一部として丸ごと実行されるため、追加のモデル変更は不要だった)。FROM句内の派生テーブルは、CTEと同様「計算済みの1つの結果」としてステップ0(実行前)のプレビュー対象に追加した。ハイライト列抽出(`_referenced_column_names`)は、サブクエリ内部で参照されている列を外側の句のハイライト対象に含めないよう、ネストしたSelectStmtの手前で探索を打ち切るよう修正した(`pglast.visitors.Skip`)。実装: `backend/app/sql_steps.py` の `_extract_from_sources`・`_ColumnNameFinder`
- [x] ウィンドウ関数 — GROUP BY/HAVINGの後・DISTINCT/ORDER BYの前に新しい「WINDOW」ステップを追加。ハイライト列は`OVER`句のPARTITION BY/ORDER BYで参照されている列。名前付き`WINDOW`句(`WINDOW w AS (...)` + `OVER w`)は、参照解決が別途必要になるためスコープ外のまま(明示的に未対応エラー)。DISTINCTを伴わない場合、WINDOWステップとSELECTステップの表示内容が一致することがある(評価順序上ここでは何も変化しないため。仕様通りの挙動)。実装: `backend/app/sql_steps.py` の `_WindowColumnFinder`・`_build_step_nodes`(WINDOW部分)
- [x] UNION / INTERSECT / EXCEPT — 2項のみ対応(3つ以上の連結は明示的に未対応エラー)。左右それぞれの枝を句分解せず「1つ目のSELECT」「2つ目のSELECT」として丸ごと実行し、続けて`UNION`/`UNION ALL`/`INTERSECT`/`EXCEPT`(必要に応じ` ALL`)の結合ステップ、トップレベルのORDER BY/LIMITがあればそれぞれ追加する。CTEと組み合わせた場合、両方の枝にWITH句を伝播する。実装: `backend/app/sql_steps.py` の `_build_setop_step_nodes`

**実装メモ(2026-09-05)**: CTE本体・UNIONの各枝・FROM句内の派生テーブルは、いずれも「それ自体をさらに句ごとに分解する」のではなく「計算済みの1つの結果」を返す1ステップとして扱う設計にした。この可視化の粒度は常に「トップレベルの1つのSELECT文」を単位とする、という一貫した方針。フロントエンドは既存のステップ配列を汎用的にレンダリングする作りだったため、これらの新しいステップ種別(WITH `<name>`・WINDOW・1つ目/2つ目のSELECT・UNION等)を追加しても`frontend/`側の変更は不要だった。

### Phase B: DML文(INSERT/UPDATE/DELETE)への対応 【2026-11-03実装済み】

SELECTの「句ごとの分解」モデルはそのまま使えず、文ごとに別の分解モデルが必要。

- [x] UPDATE文: `対象テーブル(+ FROM) → WHERE → SET → RETURNING → 実行後のテーブル`
- [x] DELETE文: `対象テーブル(+ USING) → WHERE → RETURNING → 実行後のテーブル`
- [x] INSERT文: `挿入する行(VALUES/SELECT) → INSERT(ON CONFLICT) → RETURNING → 実行後のテーブル`

元クエリに存在しない句(WHERE・RETURNING等)のステップは表示しない。ステップ0「実行前」(2-(b))と最後の「実行後のテーブル」が対になり、実行前後の状態を並べて見せる。

**実行方式**: DML文はSELECTで挙動を模倣するのではなく、**本物のPostgreSQLで実際に実行し、必ずROLLBACKする**(実際のデータは変更されない)。これにより、DEFAULT・SERIALの採番・`ON CONFLICT`・外部キー制約違反などのエラーを含め、実際の挙動をそのまま見せられる(1節の基本方針と同じ)。

- 対象行の絞り込みまで(対象テーブル・WHERE・挿入する行)は、SELECT文に組み立て直して読み取り専用で実行する。
- それ以降(SET/INSERT・RETURNING・実行後のテーブル)は、**DML文を1リクエストにつき1回だけ実行**した結果から切り出す。ステップごとに実行し直すと、ROLLBACKしても戻らないSERIALの採番がステップ間で食い違う(INSERTステップでは7番、実行後のテーブルでは8番になる等)ため。実際に投げるのは、元のRETURNING句の前に「対象テーブル.*」を足した1文で、その出力を対象テーブルの列数で「挿入・更新された行」と「元のRETURNING句の出力」に切り分ける。そのあと同じトランザクション内で対象テーブル全体をSELECTし、最後にROLLBACKする。
- 「実行後のテーブル」は主キー順に並べる。並べないと、UPDATEした行が(新しい行バージョンとして書き込まれるため)テーブルの末尾に移動して見え、実行前と見比べにくい。主キーはカタログ(`pg_index`)から取得し、主キーがない場合は並べ替えない。
- 各ステップのSQL表示は、「そのSQLを実行するとこの結果になる」ものにしている。SET/INSERTステップは`... RETURNING <対象テーブル>.*`、実行後のテーブルは`<DML文>;` と `SELECT * FROM <対象テーブル> ORDER BY <主キー>` の2文。

**各ステップの詳細**:
- UPDATEの「SET」ステップは更新後の値を表示し、SET句の列をハイライトする(実行後のテーブルでも同じ列をハイライト)。直前のWHEREステップが更新前の値なので、行き来すると変化がわかる。
- `FROM`/`USING`句を伴う場合、「対象テーブル + FROM/USING」ステップは対象テーブルとの直積になる(結合条件はWHERE句で指定するというPostgreSQLの仕様どおり)。
- INSERTの「挿入する行」ステップは、`VALUES`/`SELECT`を `SELECT * FROM (...) AS new_rows (<挿入先の列名>)` として単独実行し、挿入先の列名を付けて見せる。`VALUES`に`DEFAULT`キーワードを含む場合はINSERTの文脈でしか評価できないため、このステップを省く(次のINSERTステップで、既定値が入った実際の行を見せる)。`DEFAULT VALUES`の場合も省く。
- `ON CONFLICT`はINSERTステップのラベル(`INSERT ... ON CONFLICT DO NOTHING`/`DO UPDATE`)と説明で表し、衝突判定の列(とDO UPDATEのSET句の列)をハイライトする。衝突した行を別ステップで見せることはしていない(下記の今後の課題)。

**未対応(明示的にエラー)**: DML文のWITH句(`WITH ... UPDATE`等)、SELECT文のWITH句の中のDML(`WITH x AS (DELETE ...) SELECT`)、`WHERE CURRENT OF`(カーソル)、`MERGE`文。

**実装メモ(2026-11-03)**:
- SERIALの採番(シーケンス)はROLLBACKしても戻らないため、INSERTを試すたびに採番される値が進む(PostgreSQLの仕様)。INSERTステップの説明文にも明記している。
- 同じ理由でトランザクションを何度もROLLBACKするようになったため、`statement_timeout`の設定方法を変更した。以前はトランザクション内の`SET`で設定しており、ROLLBACKで設定ごと取り消されていた([backend/core.md 実行時の安全策](../backend/core.md#実行時の安全策)参照)。
- フロントエンドは今回もステップ配列を汎用的にレンダリングするだけで済んだ。変更はサンプルクエリ(UPDATE/DELETE/INSERT)の追加と、ステップ0の説明文の一般化のみ。
- 実装: `backend/app/sql_steps.py` の `_build_dml_steps`(`_build_update_steps`/`_build_delete_steps`/`_build_insert_steps`)・`_run_dml`・`execute_steps`

**今後の課題**:
- [ ] `ON CONFLICT`で衝突した既存の行を、別ステップとして見せる
- [ ] UPDATEのSETステップで、更新前と更新後の値を同じ行に並べて見せる(PostgreSQL 18の`RETURNING old.*, new.*`が使える)
- [ ] DML文のWITH句

> **重要**: [features/04-transaction-lock-stepper.md](04-transaction-lock-stepper.md)(トランザクション/ロックのstep-by-step可視化)に着手するには、このPhase Bが前提だった(ロック・トランザクションの挙動は書き込みを伴って初めて意味のある可視化になるため)。2026-11-03にこの前提は満たした。
