## 1. 概要

独自の実行エンジンを実装するのではなく、SQLを句の境界ごとに分解した「そのステップまでのSQL」を組み立てて、**本物のPostgreSQLに実際に投げて**結果を取得する方式。入力したSELECT文を、論理的な実行順序ごとに分解し、各ステップまでの中間結果テーブルを表示する。

実行順序: `FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT[DISTINCT] → ORDER BY → LIMIT/OFFSET`。元クエリに存在しない句のステップは表示しない。

## 2. 機能詳細

### (a) ステップ分解・データ変化の可視化

- 実装: `backend/app/sql_steps.py` の `_build_step_nodes` / `parse_to_steps` / `execute_steps`
- 各ステップの実行結果は `SELECT * FROM (<ステップSQL>) LIMIT 200` でプレビュー行数を保険的に制限([実行時の安全策](../backend/core.md#実行時の安全策)と共通の考え方)

### (b) ステップ0「実行前(元テーブル)」

FROM句が参照する実テーブルを再帰的に特定し(自己結合・多段JOINにも対応)、JOIN・絞り込みが行われる前の生データを表示する。**「実行」ボタンを押す前から**、SQL入力に対して自動(デバウンス500ms)で表示される。

- 実装: `backend/app/sql_steps.py` の `_extract_base_tables` / `preview_source_tables`

### (c) カラムハイライト

各ステップが「どの列を根拠に判断したか」を、pglastのASTから抽出して自動ハイライトする。

| ステップ | ハイライト対象 |
|---|---|
| FROM/JOIN | JOIN条件(ON句)で参照されている列 |
| WHERE | WHERE条件式で参照されている列 |
| GROUP BY | グルーピング対象列 |
| HAVING | HAVING条件式で参照されている列(`COUNT(*)`のように列を直接参照しない場合は対象なし) |
| ORDER BY | 並び替え対象列(SELECTのエイリアス指定も可) |
| SELECT / LIMIT・OFFSET | ハイライトなし |

- 実装: `backend/app/sql_steps.py` の `_referenced_column_names`(`pglast.visitors.Visitor` でColumnRefを収集)
- ステップ0の元テーブルにも、直後のJOINで使われる列を先回りしてハイライト

### (d) 表示UI 【旧実装 — 3節の新レイアウトに置き換え済み】

旧実装(縦につながるステップ表示): ページング(1ステップずつの表示切り替え)ではなく、SQL入力欄と0〜Nのステップボタンを画面上部に固定([固定ヘッダーとスクロール連動](../frontend/core.md#固定ヘッダーとスクロール連動)参照)し、その下に全ステップのカードを接続矢印つきで縦一列に常時表示していた(説明文・SQL・結果テーブルを同じカード内に表示)。

- ボタンクリック → 該当ステップの位置までスムーズスクロール
- スクロール位置 → 対応するボタンが自動でハイライト(scrollspy)
- ステップカードはフェード+スライドインで順に登場するアニメーション、ハイライト列はパルスアニメーション([アニメーション規約](../frontend/core.md#アニメーション規約)参照)

> 2026-08-31時点で、3節のレイアウトに置き換え済み(モバイル/狭幅時のフォールバックのみ未実装)。ハイライトパルスの仕組みはそのまま新レイアウトに転用している。上記は置き換え前の実装の説明として残す。

## 3. 表示レイアウトの変更仕様

**変更前(旧2-(d))**: ステップごとのカードを画面幅いっぱいで縦に積み上げ、説明文・SQL・結果テーブルを同じカード内に表示していた。

**変更後の仕様(2026-08-31、複数回の見直しを経て確定)**: ステップごとに1枚の**大きなカード**を用意し、そのカードの中を左右2分割する(左: 説明・SQLスニペット、右: 結果テーブル)。ページ・カード自体はスクロールさせず、カード1枚がまるごと次のカードに**入れ替わる**ことでステップを切り替える。

- カード表示エリア(`.step-stage`)は、画面上部の固定ヘッダーを除いた**ビューポートの残り全体にちょうど収まる固定高さ**とし、ページ本体(`window`/`body`)は一切スクロールしない。
- カードの中は左右2カラム構成:
  - **左側**: ステップ番号・ラベル・説明文・SQLスニペット。SQLスニペットは、プレーンテキスト(`<pre>`)ではなく [SQLエディタ](../frontend/core.md#sqlエディタ)と同じ編集可能コンポーネントを**読み取り専用(`readOnly`/`editable={false}`)**で配置する。将来「ステップ単位でSQLを編集し、そのステップ以降を再計算・再可視化する」機能を追加する際に、表示コンポーネントの差し替えが不要になるようにするため。今回のスコープは disabled 表示までで、編集の有効化・再計算ロジックは別途スコープを切る。
  - **右側**: そのステップの結果テーブルのプレビュー。列ハイライト(2-(c))はそのまま適用する。
- ステップの切り替え操作は2通り:
  - **マウスホイール/トラックパッド操作**: カード表示エリア上でのホイール入力を「ページのスクロール」ではなく「1ステップ進める/戻す」という離散的な操作として扱う(`wheel`イベントを`preventDefault`し、累積量が閾値を超えたら`activeIndex`を1つ進め/戻す。連続入力で複数ステップ飛ばないよう短いクールダウンを設ける)。
  - **上下ボタン**: カード右下に▲(前のステップ)/▼(次のステップ)ボタンを常設し、クリックでも1ステップずつ進める/戻せる。
  - 画面最上部の固定ヘッダーのステップ番号ボタン(0〜N)から直接指定ジャンプすることも引き続き可能。
- ステップが切り替わる際は、カード全体がフェード+わずかな上下スライドで入れ替わる(進む/戻るの向きに応じて双方向)。カード内部の結果テーブルは、それとは別に3.1節のFLIPベースのアニメーション(行/列単位)で変化を見せる。
- レスポンシブ: 画面幅が狭い場合(モバイル等)は左右2分割のカードを維持できないため、現行の縦積みレイアウト(2-(d)相当)にフォールバックすることを検討する。具体的なブレークポイントは実装時に決定する。

**この仕様に至るまでの経緯(2026-08-31、複数回の手戻り)**:
1. 最初に「左カラムを通常スクロール、右カラムを`position: sticky`で追従」という案を実装したが、ヘッダー高さの変化で右カラムの位置がずれる、最後のステップまでスクロールしきれない、という問題が発生した。
2. 次に「左カラムを固定高さの`overflow-y: auto`コンテナにし、内部スクロールだけでステップを切り替える(右カラムも同じ固定高さ)」という案に変更したが、依然としてページ全体やカード内部が「スクロールする」という見た目・挙動が残ってしまい、要件(スクロール操作はあってよいが、画面の上下移動という見た目自体をなくしたい)を満たせていなかった。
3. 最終的に、現在の仕様(ステップごとに1枚の大きなカードが丸ごと入れ替わる方式)に変更した。スクロール/ボタンは「入力」としてのみ使い、DOM要素が物理的にスクロールすることは一切なくした。

### 3.1 ステップ切り替え時のアニメーションイメージ

前のステップの結果テーブルから、次のステップの結果テーブルへ切り替わる際の見た目を、操作の種類ごとに定義する。単純なクロスフェードではなく、**その操作が実際に何をしたか**が視覚的にわかるアニメーションにする。

| ステップ種別 | アニメーションイメージ |
|---|---|
| FROM/JOIN | 複数の元テーブルが、1つのテーブルへ連結(マージ)されていくように見せる |
| WHERE / HAVING(行の絞り込み) | 条件に合わない行がその場でフェードアウトして消え、合致する行だけが残る |
| SELECT(列の絞り込み) | 選択されなかった列がフェードアウトして消え、選択された列だけが残る |

GROUP BY / ORDER BY / LIMIT・OFFSET のアニメーションイメージは未定義(下記オープン課題参照)。

**双方向性(重要な要件)**: ステップを進める方向だけでなく、**スクロールを上に戻して前のステップに戻る場合も、上記アニメーションが逆再生されるようにする**(例: JOINで連結されたテーブルは、前段に戻ると再び分離して見える。消えた行・列は前段に戻ると再度現れる)。スクロール方向(上/下どちらに進んでいるか)を検知し、アニメーションの向きをその都度切り替える必要がある。

**実装上の含み**: 単純なフェードイン/フェードアウトの切り替えでは実現できず、行・列に安定した識別子(主キーや列名)を持たせ、同一の行・列がステップをまたいでどう変化したか(残る/消える/合流する)を追跡できる仕組みが必要になる(いわゆるFLIP的な差分トランジション)。手書きCSSでこれを双方向に作り込むのはコストが高いため、[frontend/core.md](../frontend/core.md#オープン課題-カラーとuiライブラリ)で方針決定した **Framer Motion**(`layout`プロパティによる自動FLIPアニメーション、`AnimatePresence`による出入りアニメーション)の採用を前提に設計する。

**オープン課題**:
- [ ] SELECTで選択されなかった列のうち、主キー/ID列は行の同一性を示すために残す(グレーアウト等)か、完全に消すか
- [ ] GROUP BY(複数行が1行に集約される見せ方)・ORDER BY(行の並び替えアニメーション)・LIMIT/OFFSET(範囲外の行が消える見せ方)、それぞれのアニメーションイメージの具体化

**実装への影響**:
- [x] `frontend/src/App.tsx`: ステップごとの大きなカード(`.step-big-card`、内部で左右2分割)が丸ごと入れ替わる構成に変更。`activeIndex`の切り替えは、ページ・カードのスクロールではなく、ホイール入力(`wheel`イベントを`preventDefault`し、累積量が閾値を超えたら1ステップ進める/戻す)と、カードに常設した▲▼ボタンで行う。
- [x] 左側のSQLスニペット表示を `<pre>` から、`SqlEditor` を読み取り専用化したコンポーネントに置き換える(`SqlEditor.tsx` に `readOnly` プロパティを追加)。
- [x] `frontend/src/components/StepTable.tsx`: Framer Motion(`motion`パッケージ)を導入し、3.1節のステップ種別ごとのアニメーション(JOINの連結・行/列の絞り込み)を、進む/戻るの向きに応じた双方向再生つきで実装する。カード全体のフェード+スライドとは別レイヤーとして、テーブル内部の行・列単位のFLIPアニメーションを担当する。
- [x] `frontend/src/index.css`: 大きなカード1枚+左右2分割のレイアウトスタイルを追加。
- [ ] モバイル/狭幅時のフォールバック挙動の決定・実装。

**実装メモ**(2026-08-31):
- FROM/JOINと「実行前(元テーブル)」間は、行・列単位でのFLIP対応関係が取れない(複数テーブル→1テーブルで形が変わる)ため、テーブル部分をクロスフェード+収束/発散するスケール・移動アニメーションで表現し、行・列レベルの提供元追跡は行っていない。
- 行の同一性は主キーがないため、直前ステップと共通の列の値を暫定的な識別子として使用している(同値の行が複数ある場合は出現順で区別)。`SELECT *` プレビューでは結合元テーブル同士で同名列(例: `customer_id`)が重複するため、列も同様に出現順で識別している。
- GROUP BY / ORDER BY / LIMIT・OFFSET は専用のアニメーションイメージが未定義(オープン課題参照)なため、上記の行・列差分による汎用トランジションにフォールバックしている。
- レイアウト方式は3節冒頭の「経緯」に記載の通り複数回変更しており、最終的に「大きなカード1枚が丸ごと入れ替わる」方式に落ち着いた。
- 固定ヘッダーの高さ測定に`ResizeObserver`の`contentRect`を使うと、padding/borderを含まない内容ボックスの高さしか取れず、カード表示エリアの高さ計算が実際より小さくなる(ヘッダーの上下パディング+ボーダー分だけカード下端が画面下にはみ出し、`overflow: hidden`で隠れた下端のボタンが見えなくなる)バグがあった。`el.offsetHeight`(border-box)で測り直すことで解消した。

## 5. SQL構文カバレッジ(現状とロードマップ)

「将来的にはほぼすべての構文を扱えるようにしたい」という方針のもと、優先順位をつけたロードマップとして管理する。日付ではなくフェーズで管理する(4章の拡張機能ロードマップと同じ考え方)。

### 現状(MVP)で対応している構文

- [x] 単一のSELECT文
- [x] FROM(単一テーブル、複数テーブルのJOIN: INNER/LEFT等)
- [x] WHERE
- [x] GROUP BY
- [x] HAVING
- [x] 集約関数(`COUNT`, `SUM` など)
- [x] DISTINCT
- [x] ORDER BY
- [x] LIMIT / OFFSET

### Phase A: SELECT文の拡充

既存の「句ごとに分解して本物のPostgreSQLに実行させる」モデルをそのまま拡張できる範囲。優先度は上から順。

- [ ] CTE(WITH句) — まず非再帰から。再帰CTEは別途難易度が上がるため後回し
- [ ] サブクエリ — スカラサブクエリ・`IN`/`EXISTS` → FROM句内の派生テーブル → 相関サブクエリ、の順で広げる
- [ ] ウィンドウ関数 — 評価順序上、GROUP BY/HAVINGの後・DISTINCT/ORDER BYの前に新しい「WINDOW」ステップを追加する必要がある(モデル拡張が必要だが破壊的変更ではない)
- [ ] UNION / INTERSECT / EXCEPT

### Phase B: DML文(INSERT/UPDATE/DELETE)への対応

SELECTの「句ごとの分解」モデルはそのまま使えず、文ごとに別の分解モデルが必要。

- [ ] UPDATE文: `FROM/JOIN → WHERE → SET → RETURNING` のようなステップ分解
- [ ] DELETE文: `FROM/JOIN → WHERE → RETURNING` のようなステップ分解
- [ ] INSERT文: 対象列 → `VALUES`/サブクエリ → `ON CONFLICT` → `RETURNING`

`RETURNING`句の可視化は、既存の「実行前(元テーブル)」(2-(b))で作った「実行前後の状態を並べて見せる」考え方とそのまま相性が良い。

> **重要**: [features/04-transaction-lock-stepper.md](04-transaction-lock-stepper.md)(トランザクション/ロックのstep-by-step可視化)に着手する場合、このPhase Bは最低限完了させておく必要がある。ロック・トランザクションの挙動は書き込み(INSERT/UPDATE/DELETE)を伴って初めて意味のある可視化になるため、SELECT文しか扱えない現状のままでは04のシナリオを構成できない。

### Phase C: DDL・その他(優先度低)

行データを主眼に置いた今の可視化の枠組み(テーブル・ハイライト)がそのままでは使えないため、優先度は最も低い。

- [ ] CREATE / ALTER / DROP TABLE等
- [ ] インデックス関連DDL([features/06-index-performance-comparison.md](06-index-performance-comparison.md)と関連)

### 対象外(他機能へ移管)

- 複数SQL文の同時入力は、この機能というより [features/04-transaction-lock-stepper.md](04-transaction-lock-stepper.md)(トランザクション/ロックのstep-by-step可視化)が本来担うべき範囲として切り出す。
- ユーザー自身のDB/スキーマ接続は、サンプルスキーマ固定という制約であり構文カバレッジの話とは別軸([backend/core.md](../backend/core.md#オープン課題-公開ホスティングに向けたサンドボックス化)参照)。
